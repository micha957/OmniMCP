# 跨平台账号运营 Agent：产品方案草稿

状态：首个产品已确定为拼豆工坊，用户确认尚未上线。运营工作台（`cmd/agentops`）已支持产品角色、内容草稿、帖子收集、模型决策、确认队列、通知导入、数据采样、排期与本地持久化。使用方式见[工作台指南](AGENTOPS.md)。

**运行原则：AI 只负责辅助，平台上的每一次写操作都要经过用户确认。** 下文中的“参与”“回复”“发布”都表示生成提案，确认后才执行。

## 已确定的首版决策

- 平台：小红书。
- 产品：拼豆工坊，微信拼豆与照片转图纸小程序；尚未上线，先准备运营系统和内容。
- 目标：让存在相关需求的人了解并使用用户自己的小程序，同时积累账号在对应领域的影响力。
- 运行方式：AI 在用户设定的角色、账号和范围内准备内容，每条平台写操作进入确认队列，用户批准后由服务端按原内容执行。
- 人工介入：除逐条确认外，资料不足、规则要求转交、登录失效或执行结果无法确认时，形成待处理事项；结果不明的写入先核对，不自动重试。
- 起点：一个角色、一个账号，同时覆盖相关帖子下的主动参与、自身内容发布，以及这两类活动带来的后续对话。

## 产品目标

用户创建一个长期角色，绑定自己管理的平台账号，设置内容方向、互动规则和活动安排。Agent 在指定时间或收到新事件时运行，读取相关内容和历史记录，提出行动建议；用户确认后由 OmniMCP 执行，并核对结果、保存记忆。

运营应形成两个相互配合的闭环：

- **参与讨论**：发现相关帖子 → 判断具体需求 → 提供解答或介绍适用功能 → 跟进回复 → 记录使用反馈。
- **经营内容**：从常见问题和产品场景中选题 → 准备并发布内容 → 评论答疑 → 将新问题用于后续内容和产品改进。

判断没有必要发言、跳过不合适的话题，也是有效结果。运营效果优先看有效对话和可观测的小程序使用情况，发帖或评论数量用于记录投入。

## 三类日常活动

### 发现需求并参与讨论

用户提供产品适用场景、目标用户、需求词和排除话题。Agent 先通过搜索发现候选帖子，再读取正文和相关评论，判断对方的问题是否能由现有产品能力或已有知识解决。

每个候选机会记录原帖、需求摘要、匹配的产品能力、可以补充的信息，以及参与或跳过的理由。相关性应来自实际需求与产品能力的匹配，单个关键词命中不足以触发评论。

评论先回应原帖的具体问题，适合时介绍小程序和用户确认的访问方式。产品相关介绍应明确开发者或团队关系。不同帖子分别生成回答；已有讨论中没有新信息可补充时跳过。

### 跟进已经开始的对话

自己的笔记，以及在其他帖子下发出的评论，都进入跟进列表。记录原帖、根评论、父评论、发言人和自身已发送内容，识别对方是在询问功能、寻求操作帮助、反馈问题，还是继续讨论。

在配置的活动时间内，已有人回应的对话优先于寻找新帖子。先读取上下文，再回答当前问题；同一问题不重复介绍产品。对方明确拒绝继续了解时结束该推广对话，需要用户确认的承诺或无法查证的问题转交用户。

跟进可通过通知发现新回复，并用已跟进的帖子作补充轮询。每次扫描保留读取范围、最后成功时间和未完成的扫描任务，不能把部分加载解释为没有新回复。

### 主动发布内容并答疑

围绕目标用户的问题，发布场景教程、解决问题的方法、功能使用说明，以及有资料支持的产品更新。已有对话中的常见问题可以成为新选题，引用具体对话时处理个人信息。

笔记需要明确内容目的、适用人群、可验证的事实、使用的素材和访问小程序的方式。发布后自动跟进评论，将未解决的问题与产品反馈分别整理。

## 产品资料与访问方式

产品知识至少包括：名称、目标用户、核心问题、已上线功能、使用步骤、费用、限制、常见问题和允许公开的素材。用户确认的产品事实与 Agent 从平台观察到的说法分别保存。

用户选择拼豆工坊作为首推产品，并确认尚未上线。

小程序的所属平台与访问方式必须明确，例如搜索名称或通过已配置的主页入口。Agent 只使用用户确认且实际可用的方式。当前已提取部分代码功能，尚未验证线上发布状态和实际入口；产品知识使用代码事实，推广访问方式待确认后填入。

## 用户配置什么

| 配置 | 内容 | 示例 |
| --- | --- | --- |
| 角色 | 定位、表达方式、已确认的背景事实 | 以开发者或团队身份介绍产品，同时解答领域问题；具体人设待确定 |
| 目标 | 服务的人群、内容方向、运营阶段 | 找到实际有需求的用户，帮助其理解并使用小程序 |
| 知识与素材 | 产品资料、文章、图片、常见问答及来源 | 已上线功能、使用步骤、限制、截图和已确认的案例 |
| 平台账号 | 平台、账号、该平台的内容偏好 | 小红书侧重图文，知乎侧重完整解释 |
| 发现策略 | 需求词、目标场景、排除话题、候选帖子条件 | 根据产品适用场景寻找求助帖，读完上下文再判断 |
| 行动规则 | 可提议的动作、触发条件、需要交给人的情形 | 相关问题准备答复；适合时介绍产品；缺少资料时转交用户 |
| 产品入口 | 名称、所属平台、用户可用的访问路径 | 用户确认的小程序搜索名称或主页入口 |
| 活动安排 | 活跃时间、内容计划、次数与费用上限 | 每周两篇内容；每天最多十条回复 |

频率、工具权限、账号范围和费用上限由程序检查。角色语气、内容相关性和回复措辞由模型判断。平台页面和评论属于待处理内容，不能修改用户设定的规则。

## 角色、Agent 与账号的关系

- **角色模板**描述人设和表达方式，可以重复使用。
- **Agent**是一份独立运行的角色实例，拥有自己的目标、知识、记忆、计划和规则。
- **平台账号**是执行行动的身份。一个 Agent 可以绑定多个平台账号；首版每个账号由一个 Agent 负责，避免重复处理。
- 同一个 Agent 在多个平台保持一致的事实和定位，同时按平台调整内容。不同 Agent 的关系记忆和运营记录默认隔离。

小程序推广作为一份可配置的运营策略，包含产品资料、受众、发现条件、内容方向、入口和效果指标。角色、调度、记忆与行动记录保持通用；小红书插件负责平台操作，不负责决定推什么产品。以后推广其他产品或切换为纯内容运营时，可以替换策略而复用运行机制。

记忆分为已确认的角色事实、可引用的知识、内容发布记录、对话与关系记录。每条外部信息保留来源与时间，便于查证和更新。生成内容不应把角色设定扩写为未经确认的亲身经历或产品事实。

## 一次运行如何进行

1. **触发**：搜索计划到期、内容计划到期，或通知与轮询发现需要跟进的新回复。
2. **收集**：读取内容正文、评论上下文、角色知识和历史互动；过滤已处理事件。
3. **决策**：决定忽略、参与原帖讨论、回复、发布或转交用户，记录需求匹配依据与引用来源。
4. **规则检查**：核对账号、工具、时间窗口、额度和用户配置的审阅要求。
5. **确认与执行**：提案进入确认队列，用户批准后使用固定账号执行，同一账号的任务依次执行。
6. **核对**：读取平台结果，确认内容链接或回复是否存在。
7. **记录**：保存行动结果、对话变化和下一次需要跟进的事项。

评论回复必须定位到具体评论，保存平台内容 ID、评论 ID、回复关系和上下文。通知读取和已知讨论的轮询共同负责发现回复，不承诺实时收到全站消息或私信。

调度优先级建议为：待回复的既有对话 → 到期内容 → 新机会搜索。分别设置外部帖子首评、对话回复和主动发帖的额度，同一帖子首次参与去重。具体时间间隔、活动窗口和额度在配置时确定。

## 用户看到什么

- **Agent 配置**：角色、目标、知识、平台账号和规则。
- **内容计划**：选题、素材、草稿、预计发布时间和实际发布结果。
- **参与机会**：候选帖子、用户需求、匹配的产品能力、参与与跳过记录。
- **互动收件箱**：新评论、建议回复、已回复记录和需要人工处理的事项。
- **活动记录**：看到了什么、为什么采取行动、调用了什么、结果是否确认。
- **运行控制**：立即运行、暂停和恢复。平台写操作不提供跳过确认的选项。

审阅绑定具体账号、目标和内容版本；内容修改后原有确认失效。暂停后不再启动新的外部写入；已发出的操作仍需记录最终结果。

## 上线后目标范围

以一个 Agent、一个小红书账号跑通完整运营闭环，再按同样的工具接口扩展到其他平台。

1. 配置角色、知识、账号、活动安排和行动规则。
2. 配置小程序资料、访问方式、需求词和排除条件；搜索并判断相关帖子，准备参与讨论的草稿。
3. 根据知识与现有素材生成笔记，到排期时间进入确认队列。
4. 保存发帖与评论回执，将自己的笔记和参与过的讨论纳入跟进列表。
5. 读取通知与新回复，结合上下文准备针对具体评论的回复，确认后发送；例外进入待处理事项。
6. 持久化任务、事件、行动与记忆，支持重启后继续运行。
7. 展示活动记录、待处理事项和效果数据，支持暂停和恢复。

后续再扩展私信和更完整的效果分析。首版内容素材来自用户已有文件或资料。

## 效果如何判断

- **发现质量**：读过哪些候选帖子，哪些与产品有实际匹配，哪些被跳过。
- **对话质量**：参与后获得回应的讨论数、帮助解决的问题、明确表达使用意向的反馈；意向属于基于对话的判断。
- **跟进及时性**：从发现新回复到处理的耗时，以及最后成功扫描时间。尚未发现的回复不能计为已及时处理。
- **内容表现**：平台实际可读取的浏览、收藏、评论等数据，记录采样时间。
- **使用情况**：若小程序能提供渠道或活动来源数据，读取实际新增和激活数据。没有来源数据时，仅展示互动和明确反馈，不把评论量等同于使用人数。

## 与现有 OmniMCP 的衔接

现有项目承担执行底座：MCP 工具路由、平台插件、账号会话、浏览器连接、素材和工具日志。新增运营层负责模型调用、角色、规则、调度、记忆、行动记录和用户审阅，通过 MCP 接口使用底座。

各平台能力现状和实测结果见[工作台指南](AGENTOPS.md)。扩展中的账号标识只用于路由；同一平台的多个真实账号仍需要不同 Chrome Profile，Agent 不能靠切换账号标识切换实际登录身份。

当前沿用 Go 技术栈，以原子替换的 JSON 文件保存单实例运营状态，支持重启恢复；后续有多进程和更大数据量时再迁移数据库与队列。平台差异继续放在插件内。模型通过独立接口接入，具体服务和模型由配置决定。

## 可靠性要求与验收

- 同一评论事件不会因轮询或服务重启被重复安排回复。
- 同一外部帖子不会因重复搜索被再次安排首评；新的对方回复按事件和上下文分别处理。
- 区分待执行、待审阅、执行中、已成功、已失败与结果不明；发布或回复超时后，先核对平台状态，再决定是否重试。
- 同一账号的完整运营任务依次执行；现有底座的单次工具锁不能替代多步流程的协调。
- 任何写操作在批准前都不会提交；批准绑定账号、工具和内容哈希，且只生效一次。
- 模型调用有单次运行的步数、时间和费用预算，遇到无法解决的问题形成待处理事项。
- 验收至少覆盖一次相关帖参与、一次外部帖子内的指定评论跟进、一次自发内容及其评论跟进、一次重启恢复，以及一次结果不明时防止重复提交的流程。
